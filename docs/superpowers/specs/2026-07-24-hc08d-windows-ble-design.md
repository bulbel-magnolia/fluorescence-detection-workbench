# HC-08D Windows 真实 BLE 接入设计规格

状态：设计与书面规格已于 2026-07-24 通过用户确认。

同日按已编译通过的 STM32 固件接口补充串口终止符与命令响应。

## 1. 目标

Windows 桌面端直接作为 BLE Central / GATT Client 连接 HC-08D，完成双向链路验证：

```text
STM32
  → UART
  → HC-08D
  → BLE Notify / Indicate
  → Windows 桌面端
  → 原始数据、三通道曲线和本地记录

Windows 桌面端
  → BLE Write
  → HC-08D
  → UART
  → STM32
  → LED 实际开关
```

首轮实现聚焦扫描、连接、GATT 发现、通知接收、原始协议解析、LED 指令、断线恢复和真实安装包测试。科学换算、背景校正、标定、质量等级和饱和数据修正不进入本轮链路验收。


## 3. 核心产品决策

### 3.1 自适应连接

桌面端不只依赖固定 UUID。扫描阶段按兼容设备名识别 HC-08 系列，连接后枚举实际 GATT 服务和特征：

1. 优先验证服务 `FFE0` 和特征 `FFE1`。
2. `FFE1` 同时支持 Notify/Indicate 与 Write 时，使用同一特征完成双向透传。
3. 默认 UUID 不存在时，优先选择同一服务中同时支持通知和写入的特征。
4. 没有双向特征时，允许分别选择一个通知特征和一个写入特征。
5. 出现多个同等级候选项时停止自动写入，在“技术详情”中要求用户明确选择。
6. 保存已经确认的服务和特征映射。下次连接优先尝试该映射，失败后重新枚举。

设备名用于发现候选设备，GATT UUID 和特征属性用于确定真实数据通道。运行时设备标识不写入源码，MAC 地址不写入普通日志、设计文档或版本库。

### 3.2 同一工作流承载 Demo 与真实硬件

Demo 和 HC-08D 使用同一套采集页面与 `BleTransport` 接口。当前模式通过状态标签呈现，不增加独立工程调试页面。

真实设备模式不复用 Demo 分析参数。真实会话先形成原始记录，算法与标定输入齐备后再进入分析。

### 3.3 本地采集与设备控制分离

HC-08D 当前连接后持续接收 STM32 数据：

- “开始采集”开始本地会话和记录，不向 STM32 发送 `START`。
- “结束采集”结束并保存本地原始会话，不向 STM32 发送 `STOP`。
- “归零”和“校准”显示固件暂不支持，不发送虚构指令。
- “打开 LED”和“关闭 LED”分别发送 `@LED_ON\r\n`、`@LED_OFF\r\n`。

BLE 写入成功只表示指令字节已经交给传输层。桌面端继续等待 STM32 响应：收到 `LED_ON_OK` 或 `LED_OFF_OK` 后显示“设备已确认指令”，收到 `ERROR_COMMAND` 或等待超时则显示失败。成功响应确认固件已经处理命令，不将其扩展表述为传感器、光路或实验状态已经验证。

## 4. 系统架构

```text
React 页面 / 组件 / i18n
            ↓
Zustand 应用状态与检测状态机
            ↓
BleTransport TypeScript 接口
            ↓
Hc08dBleTransport
            ↓ Tauri commands / events
Rust Hc08dRuntime + btleplug
            ↓
Windows BLE
            ↓
HC-08D
```

### 4.1 表现层

采集页面负责：

- 设备发现、连接和断开入口
- 连接与数据状态
- 本地采集开始和结束
- LED 开关指令
- 480、515、555 三通道曲线
- CLR 总体亮度
- 饱和标记
- 可折叠技术详情

页面不直接访问 Tauri、btleplug 或原始字节。

### 4.2 TypeScript 传输层

新增 `Hc08dBleTransport` 并继续实现现有 `BleTransport`：

- 将扫描、连接、断开和写入转换为类型化 Tauri 命令。
- 监听设备发现、连接状态、通知字节和断线事件。
- 使用连接代次隔离迟到事件。
- 将协议帧转换为领域事件。
- 在 `dispose` 时解除全部前端监听。

`MockBleTransport` 保持独立、可重复和可测试。传输选择由一个可切换适配器或工厂管理，应用状态不再固定实例化 Mock。

### 4.3 Rust 原生层

Rust 使用 `btleplug` 的 Windows 后端承担：

- 获取 Windows 蓝牙适配器
- 扫描 BLE 广播
- 读取名称、RSSI 和运行时设备标识
- 建立连接并发现服务
- 验证特征属性
- 订阅 Notify/Indicate
- 选择 Write With Response 或 Write Without Response
- 监听通知和断线
- 取消扫描、解除订阅和释放设备

Rust 层只负责 BLE 字节传输和连接资源，不解释光强字段，也不执行分析。

### 4.4 Tauri IPC

原生命令至少包括：

- `ble_runtime_status`
- `ble_scan_start`
- `ble_scan_stop`
- `ble_connect`
- `ble_disconnect`
- `ble_select_characteristics`
- `ble_write`

原生事件至少包括：

- `ble://device-found`
- `ble://connection-state`
- `ble://notification`
- `ble://disconnected`
- `ble://error`

每个事件包含连接代次。通知事件携带受限长度的字节数组，不携带任意文件路径或未约束对象。

## 5. 扫描与连接

### 5.1 扫描

- 默认扫描 8 秒，支持用户提前停止。
- 名称匹配不区分大小写，兼容 `HC-08`、`HC08` 和可选 `D` 后缀。
- 同一运行时设备标识只展示一次，RSSI 使用最近一次广播更新。
- 普通列表显示设备名和信号强弱，不显示 MAC 地址。
- 没有适配器、蓝牙关闭和扫描失败分别映射为可恢复错误。

### 5.2 连接

- 默认连接超时 10 秒。
- 连接后执行非缓存服务发现，避免沿用过期 GATT 表。
- 特征选择完成并成功订阅后才进入“可以接收数据”。
- 第一帧有效数据到达后进入“正在接收”。
- 如果手机或另一台电脑占用设备，提示用户先断开其他终端。

### 5.3 特征选择评分

候选特征按以下优先级评分：

1. `FFE0/FFE1` 且同时支持通知和写入。
2. 其他 UUID，但同一特征同时支持通知和写入。
3. 同一服务中的一个通知特征和一个写入特征。
4. 跨服务的唯一通知、写入组合。

候选并列时返回 `CHARACTERISTIC_SELECTION_REQUIRED`，不自动试写。用户确认后的 UUID 组合按设备名称族和 GATT 结构保存，不按个人设备 MAC 固化。

## 6. 接收协议

### 6.1 帧结构

有效帧为：

```text
480:<uint16>,515:<uint16>,555:<uint16>,CLR:<uint16>
```

解析表达式采用严格字段顺序和 ASCII 字符：

```text
480:(\d+),515:(\d+),555:(\d+),CLR:(\d+)
```

每个值必须位于 0–65535。字段缺失、重复、乱序、负数或超出范围的帧不进入曲线和记录。

### 6.2 分包与帧边界

协议解析器维护最多 8192 字节的接收缓冲：

1. 支持一帧被多个 BLE 通知拆分。
2. 支持一个通知包含多帧。
3. 优先识别 `\n` 和 `\r\n`。
4. 固件的正常帧边界为 `\r\n`。
5. 为兼容 BLE 通知边界和调试输入，没有换行时仍可使用下一段 `480:` 作为前一帧结束标志。
6. BLE 通知间隔不作为帧边界；未出现换行或下一段 `480:` 时继续等待后续字节。
7. 超过缓冲上限时清空当前缓冲，产生 `PROTOCOL_BUFFER_OVERFLOW`，继续接收后续数据。

原始报文监视器只保留最近 200 条或 64 KiB，以较早达到的限制为准。

### 6.3 领域映射

每个完整硬件帧生成一个 `Hc08dSampleFrame`：

```text
sequence
receivedAt
elapsedMs
signal480
signal515
signal555
clearSignal
saturatedChannels
rawLine
```

`sequence`、`receivedAt` 和 `elapsedMs` 由桌面端补充。三个波长数据共享同一序号和时间点。

曲线映射：

| 硬件字段 | 软件通道                           |
| -------- | ---------------------------------- |
| `480`    | `channel1` / 480 nm                |
| `515`    | `channel2` / 515 nm                |
| `555`    | `channel3` / 555 nm                |
| `CLR`    | 总体亮度参考，不作为第四个分析通道 |

数值在普通界面标为“原始值”。软件不把 CLR 当作背景，不生成校正信号、浓度或质量等级。

### 6.4 饱和值

值等于 65535 时：

- 保留原始数值。
- 正常进入曲线和本地记录。
- 添加对应通道饱和标记。
- 使用文字或图标提示，不只依赖颜色。
- 不触发连接错误，不中断本轮链路测试。

## 7. 发送协议

LED 指令使用固定 ASCII 字节：

```text
@LED_ON\r\n
@LED_OFF\r\n
```

编码器必须满足：

- 不添加空格。
- 不添加 NUL。
- 每条命令只添加一个 `\r\n`。
- 不使用 JSON 包装。

特征同时支持两种写入时优先使用 Write With Response。仅支持 Write Without Response 时允许发送，同时继续使用“指令已发送”的界面语义。

### 7.1 固件响应与命令关联

固件响应同样使用 ASCII 和 `\r\n`：

```text
LED_ON_OK\r\n
LED_OFF_OK\r\n
ERROR_COMMAND\r\n
```

桌面端一次只允许一个 LED 命令等待响应，以便在没有命令 ID 的协议中可靠关联结果：

1. BLE 写入完成后，命令状态进入“等待设备确认”。
2. `LED_ON_OK` 仅完成当前 `LED_ON`，`LED_OFF_OK` 仅完成当前 `LED_OFF`。
3. `ERROR_COMMAND` 将当前命令标记为设备拒绝。
4. 响应类型与等待命令不匹配时记录 `UNMATCHED_COMMAND_RESPONSE`，不误报成功。
5. 2 秒内没有收到响应时产生 `COMMAND_RESPONSE_TIMEOUT`。
6. 断线、主动断开或传输释放会取消等待中的命令。

### 8.1 普通连接状态

```text
→ 正在查找设备
→ 正在连接
→ 正在准备数据通道

```

## 9. 本地记录与分析边界

真实 HC-08D 会话保存为 `hardware-live` 原始记录：

- `isDemo = false`
- `protocolVersion = HC08D-ASCII-DRAFT-0.2`
- `algorithmVersion = null`
- `calibrationVersion = null`
- `resultStatus = RAW_ONLY`
- 不生成 Demo 质量等级

SQLite 增加版本化迁移，为每帧保存：

- 会话或记录 ID
- 序号和接收时间
- 480、515、555、CLR 原始值
- 饱和位掩码
- 原始文本

现有 Demo `channel_samples` 和分析结果保持兼容。真实原始记录进入分析前必须显式选择已批准的背景、标定和算法版本。

## 10. 断线与恢复

- 用户主动断开时立即取消扫描、订阅、重连和接收任务。
- 意外断开时分别等待约 1、2、4 秒，最多自动重连三次。
- 重连成功后重新发现服务、选择特征并订阅，不复用旧特征句柄。
- 重连期间保留当前本地会话和已接收数据，在时间轴上记录中断区间。
- 三次失败后停止自动重试，提供“重新连接”。
- 应用退出、切换传输模式或连接其他设备时释放全部 BLE 资源。
- 连接代次阻止旧扫描、旧通知和旧断线回调覆盖当前状态。

需要覆盖：

- `BLUETOOTH_ADAPTER_UNAVAILABLE`

- `SCAN_FAILED`
- `DEVICE_NOT_FOUND`
- `CONNECTION_TIMEOUT`
- `CONNECTION_LOST`
- `SERVICE_NOT_FOUND`
- `CHARACTERISTIC_NOT_FOUND`
- `CHARACTERISTIC_SELECTION_REQUIRED`
- `NOTIFY_UNSUPPORTED`
- `WRITE_UNSUPPORTED`
- `SUBSCRIBE_FAILED`
- `WRITE_FAILED`
- `COMMAND_BUSY`
- `COMMAND_RESPONSE_TIMEOUT`
- `UNMATCHED_COMMAND_RESPONSE`
- `DEVICE_COMMAND_REJECTED`
- `INVALID_UTF8`
- `MALFORMED_FRAME`
- `PROTOCOL_BUFFER_OVERFLOW`
- `DATA_STALE`

协议错误只跳过当前无效帧。连接错误提供重试或重新扫描入口。日志记录层级、事件、时间、连接代次和安全的设备别名，不记录 MAC 地址、私有实验数据全集或凭据。

## 13. 实机冒烟测试

1. 手机和其他电脑先断开 HC-08D。

## 14. 首轮完成标准

- Windows 能发现并连接 HC-08D。
- 默认或自适应 GATT 特征选择成功。
- 每 0.5 秒左右持续收到并解析真实报文。
- 480、515、555 和 CLR 正确显示与保存。
- 65535 被标记为饱和且不阻断链路。
- LED 开关指令按带 `\r\n` 的 ASCII 发送，软件正确显示 STM32 成功或错误响应，硬件产生可观察响应。
- 主动断开、意外断开和重连行为符合设计。
- 真实会话不进入 Demo 科学分析。
- 自动化检查和 Windows 安装包构建通过。
- 至少完成一台真实 Windows 电脑与 HC-08D 的双向冒烟测试。

## 15. 后续阶段

后续协议演进包括：

- 带命令 ID 的可并发 ACK 协议
- 设备时间戳或硬件序号
- 设备状态与错误码
- 背景采集与归零
- 标定参数和版本
- 饱和处理策略
- 科学分析和质量评价
- Android 与 Windows 的共享测试向量

这些能力在对应硬件和实验定义确认后按版本加入，不改变本规格建立的传输、协议和分析分层。
